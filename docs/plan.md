## 1. 목적
소비자가 공개적으로 남긴 결함 신고를 증상별로 분류해, **어떤 증상이 신고에서 얼마나 자주 언급되는지**, **리콜 이후에도 신고가 이어지는지**를 확인한다. 신고 수는 실제 고장 수가 아니다. 같은 차량의 중복 신고도, 신고되지 않은 고장도 있을 수 있다. 그 결과로 정비 현장에서 쓸 수 있는 **증상별 점검 순서 가설**을 만든다. 정비 경험이 없으므로 결론은 가설로 두고, 현장 검증이 필요한 부분을 명시한다.

## 2. 배경

**현재의 문제**
- 전기차는 내연기관차와 고장 양상이 다르다. 고전압 배터리, 충전 장치, 12V 계통이 서로 얽혀 있어 하나의 증상이 여러 원인에서 나올 수 있다.
- 신고 한 건은 개인의 경험이지만, 수백 건을 모으면 반복되는 증상과 순서가 보인다.
- 리콜이 시행돼도 같은 증상이 다시 신고되면, 조치의 효과나 대상 범위를 다시 볼 필요가 있다.

**데이터로 확인할 수 있으면**
- 문진 단계에서 어떤 질문을 먼저 해야 할지 근거가 생긴다.
- 리콜 이행 여부와 조치 후 고장 사례를 구분해 품질 이슈로 올릴 대상을 고를 수 있다.

## 3. 문제 정의
아이오닉5 2022~2025년식 공개 결함 신고에서
1. 증상별 빈도와 연식별 차이는 어떤가?
2. 가장 많은 증상은 어떤 순서로 나타나는가?
3. 관련 리콜 이후 신고가 줄었는가, 조치 후 고장을 서술한 신고는 어떤 특징이 있는가?
4. 이를 바탕으로 증상별 점검 순서를 어떻게 세울 수 있는가?
5. 지능형자동차 수업에서 다룬 인지 센서와 운동 제어 기능, 즉 ADAS 기능에 대한 신고는 어떤 기능·센서·오류 유형으로 나뉘고, 어떤 조건에서 나타나는가? 정비 이력은 점검 순서의 어디에 들어가야 하는가?
6. ADAS 신고에 나온 "레이더 가림과 함께 크루즈가 꺼지며 급감속"을 수업에서 배운 차량 종방향 운동, 피드백 제어, 센서 오차로 MATLAB에서 다시 만들면, 간격 제어의 오버슈트와 레이더 오차·해제 방식의 영향은 어떻게 나타나는가?

## 5. 범위

**포함**
- 데이터: NHTSA 공개 결함 신고와 리콜 정보, 아이오닉5 2022~2025년식
- 키워드 규칙 분류와 표본 검토
- 신고 패턴과 리콜 조치 내용을 근거로 한 점검 순서 가설
- ADAS 기능 신고: 스마트 크루즈, 차로 유지, 전방 충돌 방지·비상 제동, 운전자 주의 경고, 카메라·레이더 언급 신고
- 스마트 크루즈 시뮬레이션: 강의자료 차량동역학 식 2-10, 3-1, 4-4의 종방향 운동, 단순 피드백 간격 제어기, 지능형자동차 05 Perception을 바탕으로 한 레이더 오차 모델. 차량 값은 모두 가정값이며 아이오닉5 공식 제원이 아님

**제외**
- 실제 차량 진단, 정비 매뉴얼, 제조사 내부 데이터
- 국내 신고 데이터
- 고장 원인의 확정

## 6. 성공 기준
1. 연식별 신고 수가 API 응답과 일치하고, 스크립트 한 번으로 모든 결과가 다시 만들어진다.
2. 분류 정확도를 표본 100건으로 측정해 수치로 보고한다. 정확도가 낮은 범주는 그대로 밝힌다.
3. 리콜 전후 신고 추이를 같은 기준으로 비교한다.
4. 점검 순서표의 각 단계에 근거가 된 신고 패턴이나 리콜 조치를 연결한다.
5. 각 결과에 한계를 명시한다.
6. ADAS 분류는 기능, 관련 센서, 오류 유형을 따로 판정하고, 오류 유형은 "필요 없는데 작동", "필요한데 미작동", "경고 과다", "기능 꺼짐·사용 불가"로 나눈다. 강의자료와 연결할 때는 강의 내용으로 설명 가능한 범위만 쓰고, 원인을 단정하지 않는다.
7. 시뮬레이션은 신고를 증명하는 데 쓰지 않고, 신고에 나온 상황을 수업 내용으로 설명할 수 있는지 보는 데 쓴다. 제어기 이득 선택 기준을 먼저 정하고, 필터 효과는 지연 증가와 함께 보고한다. 강의자료에서 가져온 식과 새로 만든 부분을 구분한다.

## 7. 리스크와 대응

| 리스크 | 대응 |
|---|---|
| 신고는 소비자 서술이라 원인이 확인되지 않음 | "언급" 기준으로 세고, 결론은 가설로 둔다 |
| 키워드 분류가 부정확함 | 1.5단계 표본 검토로 정확도를 측정해 보고 |
| 신고 수 증가가 언론 보도 등 외부 요인일 수 있음 | 추이를 해석할 때 단정하지 않고 가능성으로 서술 |
| 고장 코드 의미를 공개 자료로 확인 못 할 수 있음 | 확인되지 않은 코드는 "미확인"으로 표기 |
| 정비 경험이 없어 점검 순서가 비현실적일 수 있음 | 리콜 조치 내용 범위 안에서만 작성, 현장 검증 필요 명시 |
| ADAS 신고는 약 93건으로 적고, 정비 이력을 직접 언급한 신고는 5건뿐 | 비율보다 유형과 조건 정리에 초점. "정비 이력 분석"을 주제로 내세우지 않고 점검 순서의 한 단계로 둠 |
| ADAS 신고는 운전자의 기대와 실제 기능 범위 차이에서 나온 것일 수 있음 | 오류 유형과 별도로 "기능 설계상 동작일 가능성"을 판정 항목에 둠 |
| 시뮬레이션이 실제 차량과 다를 수 있음 | 결론을 "이 모델에서는"으로 한정, 가정값 민감도 확인. 해제 방식은 두 경우를 비교만 하고 실제 차량이 어느 쪽인지 단정하지 않음 |

## 8. 공개 시 주의
- NHTSA 데이터는 미국 정부 공개 자료다. 원본은 API로 다시 받을 수 있으므로 저장소에는 받는 스크립트만 올리고, 원본 JSON은 올리지 않는 방안을 검토한다.
- 신고 본문에는 판매점 이름 등이 들어 있다. 결과 문서에 본문을 인용할 때는 짧게, 개인을 특정할 수 있는 내용은 빼고 인용한다.
